# RUN 003 — Upload-to-review end-to-end flow

The local ConsentDocs server was started with the API key loaded from the
private `0600` secret file. The key was not passed to the browser.

## Verified sequence

1. `GET /api/health` returned `status=ok`, `provider=nutrient-dws`, and
   `keyConfigured=true` without returning the key.
2. A generated `missing-withdrawal.pdf` was uploaded to `POST /api/analyze`.
3. The server kept the file in memory and called the real Nutrient DWS extract
   endpoint.
4. DWS returned HTTP `200` with request ID `GMyns8cW-_n3F4QAAE8S`.
5. Local policy returned `needs_review` with
   `withdrawal_method=missing`.
6. `POST /api/review` recorded an explicit human approval rationale.
7. The review event's `previousHash` exactly matched the extraction event hash,
   producing a valid append-only chain.
8. Static assets were served by the same process and exposed the real upload
   control.

## Security checks

- Upload size is limited to 10 MiB and one file.
- Non-PDF MIME types are rejected before provider execution.
- Request bodies and authorization headers are redacted from logs.
- The server does not write uploaded files or raw provider responses to disk.
- Production dependency audit reports zero vulnerabilities.
